# 失败案例复盘（症状 → 根因 → 修复 → 教训）

> 一次 Unity 日文游戏静态汉化中真实踩过的 5 个坑。按发现顺序排列。
> 每个案例都用"症状 → 错误归因 → 实际根因 → 修复 → 教训"结构复盘，
> 供后续 agent 快速对号入座。

---

## 案例 1：启动即崩（Unity 崩溃弹窗）

- **背景**：为了启用 TMP 运行时补字，把图集纹理设为可写（`m_IsReadable=true`）。
- **症状**：游戏启动加载阶段直接弹出 Unity 崩溃对话框，随后进程退出。
- **诊断**：与上一可启动版本逐字节 diff——纹理对象**只有 1 个字节**变化（该 bool）。
  排除序列化损坏 → 判定为"可写纹理 + .resS 流式大纹理 + 动态字体写入"的加载/渲染
  路径崩溃。
- **修复**：回滚该标志；彻底放弃运行时补字，改静态烘焙。
- **教训**：
  - 修改前后做**字节级 diff** 是最廉价的定位手段（能把"资产坏了"与"功能触发了"分开）；
  - TMP Dynamic 补字在此游戏 = 死路：不可写 → 静默失败；可写 → 崩溃。

## 案例 2：所有运行时补字静默失败（方块字之源）

- **症状**：静态图集里已有的字显示正常；不在静态表里的字全部方块。
- **根因**：`m_IsReadable=false` 的图集在构建时丢弃 CPU 侧像素数据，
  FontEngine 无法在运行时写入新字形 → **所有**动态补字静默失败。
  （此前"对话框大体能读"只是因为那些字恰好烘焙在静态图集里。）
- **教训**：
  - 遇到"部分缺字"，先按**字符来源**分组统计（静态覆盖 vs 需要动态），
    若"需要动态的全部失败"则是系统性失败，不是覆盖问题；
  - 修复系统性失败的尝试若引发更糟的症状（案例 1），说明路线本身要换。

---

## 案例 3：部分字显示成"别的字"（字形 ID 空间冲突）

- **症状**：烘焙完成后，部分简化字显示成对应的日文/繁体字形（如 绪→緊邻的日文字形），
  另一部分正常；比例约九成错、一成对。
- **根因**：TMP 按 **glyphIndex** 在字形表字典查重（同 index 取表中靠前的记录）。
  静态字形 ID 已整体 +100000（→100001~107864），但烘焙字形用的是子集字体 glyphID
  **+100000**（→100000~106700）——**两段区间几乎完全重叠**，烘焙字被静态表的
  日文字形顶掉。没撞车的那 ~10% 才显示正确。
- **修复**：烘焙字形 ID 改用 **+200000** 的独立区间（200001~206700）。
- **教训**：
  - "把两个空间都加同一个偏移"≠"错开"；必须验证**区间不相交**；
  - 写一个断言：静态 ID 集合 ∩ 烘焙 ID 集合 = ∅，且整体无重复；
  - 抽查出错字符的 glyphIndex 归属（静态/烘焙）是 30 秒定位法。

## 案例 4：一个字格里挤着两个字（叠字）

- **症状**：部分字符位置渲染出**两个汉字叠印**；从图集抠像素验证，
  单元内确实印着两个字形。
- **根因**：序列化的 free rect list **本身互相重叠 7406 对、与 used 区重叠 18203 对、
  总量虚报**（声称 14.8M px 空闲，实际静态字形已占 97%）。装箱器把它当互斥空间 →
  597 个字形被写进互相重叠的区域（烘焙字形间重叠 10520 对）。
- **修复**：占用网格（bytearray）标记静态 used 区，装箱时逐格校验零重叠；
  容量不足的部分改走**第二图集**（见案例 5）。
- **教训**：
  - 资产里序列化的"自由空间"记账可能是过时的、错误的——**用占用网格自管**；
  - 装箱后做"字形×字形重叠对 = 0"的自检（按 atlasIndex 分组统计还能顺便定位
    哪一类字形出的问题）。

## 案例 5：只放下一小部分字形（图集物理容量不足）

- **症状**：修好叠字后，597 个字形只成功放置 30~79 个，其余报"装不下"。
- **根因**：实测原版图集静态字形占用 **97%**（65.3M/67.1M px），真实空闲仅 ~1.8M px，
  装不下 597 个全尺寸中文字形（需 ~6M px）。序列化 free list 声称的 14.8M px
  空闲是虚报（与实际占用对不上）。
- **修复**：**第二图集**——把一张内容交换后已无人引用的旧图集纹理追加为
  `m_AtlasTextures[1]`，新字形 `atlasIndex=1`，全尺寸烘焙进它（该纹理 8192² 全部可用）。
- **教训**：
  - 图集容量必须用 **used rects 的实际面积和**核算，不能用 free list；
  - TMP 的多图集（`m_AtlasTextures` 数组 + `glyph.atlasIndex`）是标准功能，
    运行时自动为非主图集字形生成子网格材质；
  - "被内容交换腾空的旧图集纹理"是零成本的容量来源。

## 案例 6（方法论）：两次"修复"后症状不变 → 理论错了

- **现象**：修正字形 ID 区间后，进游戏截图与修复前几乎一致。
- **处理**：不再继续在错误理论上打补丁，而是**从图集像素层直接取证**
  （把出错字符的图集单元抠出来渲染成 PNG）——像素层就叠字 → 数据层问题，
  与索引理论无关 → 转向检查装箱重叠。
- **教训**：
  - **像素级取证**（抠图集区域渲染 PNG 人工看）是字体问题最强的定位手段，
    一次目视顶十次推理；
  - 修复后症状不变 = 理论错误，立即重找根因，不要叠加修复；
  - 让用户提供的截图按"界面 + 字号 + 具体字符"对应到数据层验证点。
